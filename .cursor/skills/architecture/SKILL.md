# Architecture & Code Structure

## Project Structure

Follow the established structure in @src/:

```
src/
├── app/                    # Next.js App Router pages
│   ├── (external)/        # Public routes (no auth)
│   └── (main)/            # Authenticated routes
│       ├── auth/          # Authentication pages
│       └── dashboard/     # Main application
├── components/            # Reusable components
│   ├── ui/               # shadcn/ui components (DO NOT EDIT)
│   └── data-table/       # Data table components
├── config/               # Application configuration
├── data/                 # Mock/static data
├── hooks/                # Custom React hooks
├── lib/                  # Utility libraries
│   ├── preferences/      # Theme/layout preferences
│   └── fonts/           # Font configurations
├── navigation/           # Navigation configs
├── server/              # Server actions & API
├── stores/              # Zustand state stores
└── styles/              # Global styles and presets
```

## Route Organization

### App Router Patterns

- Use **route groups** for logical organization: `(main)`, `(external)`
- Place page-specific components in `_components` folders
- Use `layout.tsx` for shared layouts within route groups
- Keep pages (`page.tsx`) minimal - delegate to components

**Example:**
```
dashboard/
├── crm/
│   ├── _components/      # CRM page components only
│   │   ├── columns.crm.tsx
│   │   ├── schema.ts
│   │   └── insight-cards.tsx
│   └── page.tsx          # Minimal, composes components
```

### File Naming Conventions

- **Pages**: `page.tsx`
- **Layouts**: `layout.tsx`
- **Components**: `kebab-case.tsx` (e.g., `user-profile.tsx`)
- **Utilities**: `kebab-case.ts` (e.g., `table-utils.ts`)
- **Types/Schemas**: `schema.ts`, `types.ts`
- **Configs**: `*.config.ts` (e.g., `crm.config.ts`)
- **Server Actions**: `server-actions.ts`

## Component Organization

### UI Components (shadcn/ui)

Located in `@/components/ui/` - **DO NOT EDIT DIRECTLY**

These are generated by shadcn CLI. To modify:
1. Extend them in separate files
2. Create wrapper components
3. Use composition, not modification

### Feature Components

Place in `_components` folder within the feature's route:

```typescript
// ✅ Good: Co-located with feature
app/dashboard/crm/_components/insight-cards.tsx

// ❌ Bad: Generic components folder
components/crm/insight-cards.tsx
```

### Shared Components

Place truly reusable components in `@/components/`:

```typescript
// ✅ Good: Used across multiple features
components/data-table/data-table.tsx
components/simple-icon.tsx

// ❌ Bad: Feature-specific in shared location
components/crm-specific-widget.tsx
```

## Module Boundaries

### Server vs Client

- **Server Components**: Default in App Router
- **Client Components**: Mark with `"use client"` directive
- Keep `"use client"` boundary as high as possible
- Don't mix server and client code in same file

```typescript
// ✅ Good: Clear boundary
"use client";

import { usePreferences } from "@/stores/preferences/preferences-store";

export function ThemeSwitcher() {
  const { theme, setTheme } = usePreferences();
  // Client-only logic
}

// ❌ Bad: Server action in client component
"use client";
import { updateUser } from "@/server/server-actions"; // Wrong!
```

### Server Actions

- Place all server actions in `@/server/server-actions.ts`
- Mark with `"use server"` directive
- Never call server actions from client components directly during render
- Use with `useTransition` or `useActionState` hooks

## Code Organization Principles

### Separation of Concerns

1. **Data Layer**: `@/data/`, `@/server/`, TanStack Query hooks
2. **Business Logic**: Custom hooks in `@/hooks/`, utility functions in `@/lib/`
3. **Presentation**: React components
4. **State Management**: Zustand stores in `@/stores/`
5. **Configuration**: `@/config/`, `*.config.ts` files

### Dependency Flow

```
UI Components → Hooks → Stores/Services → Server Actions → Data
```

- Components should never import directly from `@/data/`
- Use hooks or stores as intermediaries
- Keep components focused on presentation

### File Size Limits

- **Components**: Max 300 lines (split into smaller components)
- **Hooks**: Max 150 lines (extract helper functions)
- **Utilities**: Max 200 lines (create separate files)
- **Pages**: Max 100 lines (delegate to components)

## Import Organization

Follow Biome's configured import order:

```typescript
// 1. React
import { useState, useEffect } from "react";
import type { ReactNode } from "react";

// 2. Next.js
import Link from "next/link";
import { useRouter } from "next/navigation";

// 3. External packages
import { useForm } from "react-hook-form";
import { zodResolver } from "@hookform/resolvers/zod";

// 4. Aliases (@/)
import { Button } from "@/components/ui/button";
import { usePreferences } from "@/stores/preferences/preferences-store";

// 5. Relative imports
import { schema } from "./schema";
import type { FormData } from "./types";
```

Run `npm run check:fix` to auto-organize imports.

## Modular Architecture

### Creating New Features

1. **Create feature folder** in appropriate route group
2. **Add `_components` subfolder** for feature components
3. **Create `schema.ts`** for data validation
4. **Add `types.ts`** if complex types needed
5. **Create `*.config.ts`** for feature configuration
6. **Build `page.tsx`** that composes components

### Scaling Patterns

- Use composition over inheritance
- Favor small, focused components
- Extract reusable logic into hooks
- Keep state close to where it's used
- Use Zustand for global state only
